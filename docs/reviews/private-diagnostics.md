# Private diagnostics follow-up

This patch builds on `integration/upstream-sync` at `8f879f99f604e73bfc3f3faa44642b7cec1ed2fa`. Its application/test source tree is `c28d4c8b5d9e1a22215ff4ab3a427a05a0420176`; code commit `eb435b94f9d4e776aa8cca520f42017984ed2879` is followed only by documentation.

## Problem and change

Removing explicit input/output logs did not cover exception payloads or secondary error propagation. Throwable messages, causes and suppressed errors can include private content; several app paths also directly logged visited URLs, image URIs, document names/paths, caller-supplied language/voice strings and native error strings. File-error UI forwarding and steered-translation error logs could reintroduce details after an earlier layer handled them.

`redactedException` creates a separate diagnostic throwable containing the original exception class name and code-generated stack frames. It neither copies nor traverses messages, causes or suppressed exceptions, and does not mutate the error used by the UI or callback. All reviewed app Log throwable arguments use this helper. Content-bearing string diagnostics in text translation, document/image handling, browser navigation/filtering, downloads, speech requests and model conversion are replaced with fixed operation labels. Useful timing, count and state diagnostics remain.

This also removes eager construction of full voice-name and rule-filename lists solely for logging. No runtime speedup, frame-time or battery improvement has been measured. Successful processing paths introduce no exception redaction work; failures allocate a diagnostic throwable and copy its stack frames in exchange for retaining useful code locations.

## Validation

They verify redaction of direct/cause/suppressed payloads, preservation of the original error, avoidance of original message/string conversion, and bounded handling of cyclic cause/suppression graphs. The original unredacted control output contains the synthetic canaries, so the negative checks are not vacuous.

## Limits and next evidence

This is Kotlin app-diagnostic hardening, not a complete audit of native engines, WebView/system logs, crash reporting, OS backups or every future logging call. Stack frames are assumed to be generated by code, not supplied by a caller. UI errors deliberately retain their original detail. No networking policy, permission or translation behavior changes are included. A phone Logcat exercise with synthetic content and failure paths remains pending.

Separate findings for subsequent focused work:

- Browser image decoding: `TranslatorJsBridge.translateImageDataUri` bounds text batches but has no corresponding image-payload/dimension budget, and full bitmap decode follows a return from a background context. Confirm dispatching and exercise malformed/oversized inputs before setting limits.
- Image cleanup: the `retranslateInto` catch in TranslationCoordinator explicitly unlocks the output, and its finally also unlocks it. The duplicate call is visible in source; actual device impact has not been established. Verify and correct this as a separate resource-lifetime change.
- Backup rules remain the empty samples. Audit the actual stored data domains and restore expectations before changing backup policy.
- The previously prepared native PDF parser update remains separate and unintegrated, as recorded in the continuation guide.

No upstream submission, master merge, release or newly distributed test APK is included.
